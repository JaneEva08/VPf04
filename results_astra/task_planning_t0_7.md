# План разработки MVP SaaS для управления задачами

## 1. Цель и границы MVP

**Цель:** к концу 8-й недели запустить веб-приложение для пилотных команд, в котором пользователи могут зарегистрироваться, создать проект, пригласить участников, распределить задачи и получать уведомления о приближающихся дедлайнах.

**Критерии готовности:**
- Все обязательные пользовательские сценарии работают в production.
- Данные проектов доступны только их участникам.
- Уведомления не дублируются при повторном запуске обработчика.
- Нет известных критических ошибок, блокирующих основные сценарии или нарушающих изоляцию данных.
- Не менее 5 пилотных пользователей проверили продукт; минимум 80% смогли самостоятельно выполнить сценарий «создать проект → пригласить участника → назначить задачу».

### Допущения для реалистичного планирования

- Каждый разработчик доступен на **30 часов продуктивной работы в неделю**, остальное — коммуникации, ревью и организационные задачи.
- Дизайнер доступен примерно на **15 часов в неделю**, с основной нагрузкой в первые две недели.
- Отдельного QA и DevOps нет: эти обязанности распределяются между разработчиками.
- Один из frontend-разработчиков координирует работу; владелец продукта со стороны заказчика принимает решения по объему.
- Используется **готовый сервис аутентификации**, а не собственная реализация паролей и восстановления доступа.
- Мобильное приложение, платежи и корпоративные интеграции в MVP не входят.

> Основное ограничение — один backend-разработчик. Поэтому фиксируем API в начале проекта, frontend разрабатываем на моках, а сложные функции сознательно упрощаем.

### Упрощенная модель доступа

- **Владелец проекта:** управляет проектом, приглашениями и участниками.

- Исполнитель должен быть участником проекта.
- Отдельные организации/workspace пока не вводим: границей доступа является проект.

## 3. Архитектура и недорогие инструменты

| Область | Решение | Причина |
|---|---|---|
| Frontend | React + TypeScript + Vite | Соответствует компетенциям команды |
| UI | Готовая библиотека компонентов | Снижает затраты на дизайн и верстку |
| Backend | FastAPI + SQLAlchemy + Alembic | API, бизнес-логика и миграции |
| База и Auth | Supabase PostgreSQL + Auth | Меньше собственной инфраструктуры |
| Проверка доступа | FastAPI проверяет токены и членство в проекте | Единое место контроля доступа |
| Email | Resend / Brevo либо аналогичный сервис | Бесплатные или недорогие стартовые тарифы |
| Напоминания | Периодический worker + таблица доставок | Без Redis/Celery на этапе MVP |
| Хостинг | Статический frontend + небольшой платный backend/worker | Предсказуемее бесплатного backend со «сном» |
| CI/CD | GitHub Actions | Автоматические проверки и деплой |
| Тесты | pytest, React Testing Library, Playwright | API, компоненты и сквозные сценарии |
| Мониторинг | Структурированные логи + Sentry или аналог | Быстрая диагностика ошибок |
| Управление | GitHub Projects | Без дополнительных лицензий |

**Ориентир инфраструктурного бюджета:** примерно **$20–60 в месяц** на пилотную нагрузку, без оплаты труда; домен оплачивается отдельно. Тарифы, коммерческие ограничения бесплатных планов, доступность резервных копий и лимиты email нужно проверить на первой неделе.

**Важно:** production-напоминания нельзя строить на сервере, который может непредсказуемо засыпать.

## 6. Зависимости и критический путь

### Основные зависимости

```text
T1 → T2, T3, T4
T3 + T4 → T5
T5 → T6 → T7
T6 + T7 → T8
T8 → T9, T10
T5–T10 → T11
T11 + T12 + T13 → T14 → T15
```

- UI можно разрабатывать после T2/T3 на моках, не ожидая готовности backend.
- T12 выполняется постепенно, начиная с регистрации, а не откладывается на конец.
- Подготовка мониторинга и резервного копирования начинается с T4; T13 — итоговая проверка.
- Подключение email-провайдера и настройка домена начинаются на Н1–2, хотя логика уведомлений реализуется на Н5.

### Предварительный критический путь

**Модель/API → Auth → проекты и права → участники → задачи → уведомления → интеграционная приемка → пилот → релиз.**

Backend находится практически на полной загрузке с учетом резерва. Задержка на этой цепочке непосредственно угрожает сроку. После первой недели критический путь нужно уточнить по фактической скорости и готовности внешних сервисов.

## 7. Правила уведомлений: зафиксировать до разработки

Чтобы не расширять задачу незаметно, в MVP принимаем следующие правила:

1. Один канал — **email**, получатель — текущий исполнитель.
2. Одно напоминание за 24 часа до дедлайна; worker проверяет очередь каждые 15 минут.
3. Для задачи, созданной или назначенной менее чем за 24 часа до будущего дедлайна, напоминание отправляется при ближайшей проверке.
4. Завершенные, удаленные, просроченные задачи и задачи архивного проекта не уведомляются.
5. Перед отправкой повторно проверяются исполнитель, дедлайн и статус.
6. Изменение дедлайна создает новое событие напоминания; повторная обработка того же события не создает дубликат.
7. При временной ошибке выполняются ограниченные повторные попытки; окончательная ошибка видна в журнале.
8. Нет персональных расписаний, push-уведомлений и ежедневных дайджестов.

Ключ защиты от дублей должен учитывать задачу, получателя, дедлайн и тип уведомления.

## 9. Чекпоинты, метрики и управление изменениями

### Контрольные точки

| Когда | Условие прохождения |
|---|---|
| Конец Н1 | Согласованы объем, прототип основных потоков, модель прав и API; проверены тарифы сервисов |
| Конец Н2 | Вход и регистрация работают на staging, CI проходит |
| Конец Н3 | Два пользователя совместно работают в проекте; посторонний не имеет доступа |
| Конец Н4 | Работает создание и назначение задачи с дедлайном и статусом |
| Конец Н5 | Полный пользовательский сценарий и тестовая email-доставка работают |
| Конец Н6 | Feature freeze; критические тесты проходят, восстановление данных проверено |
| Конец Н7 | Пилот завершен, блокирующие дефекты устранены |
| Конец Н8 | Production-релиз принят, мониторинг и эксплуатационные инструкции переданы |

### Метрики готовности

- **Функциональность:** 100% Must Have приняты по критериям.
- **Качество:** 0 открытых критических и высокоприоритетных дефектов, влияющих на основные сценарии.
- **Безопасность:** все автоматизированные проверки изоляции проектов проходят.
- **Уведомления:** в контролируемом тесте не менее 95% событий передаются email-провайдеру в течение 30 минут от расчетного времени; дубликатов нет. Доставку во входящие отслеживаем отдельно.
- **Производительность:** целевой p95 основных API — до 700 мс при согласованном тесте, например 20 одновременно активных пользователей.
- **Пользовательский результат:** минимум 80% пилотных пользователей самостоятельно проходят основной сценарий.

### Рабочий процесс

- Недельные итерации с демонстрацией результата.
- Ежедневная короткая проверка блокеров.
- Максимум одна основная задача в работе на человека.
- Ревью PR — в течение одного рабочего дня.
- Еженедельный пересчет остатка работ и резерва.
- Если отставание превышает 3 рабочих дня: сначала исключаем Should Have/Nice to Have, затем упрощаем UX без потери обязательных сценариев.

**Итог:** срок в 8 недель достижим при готовом Auth, простых ролях, списочном интерфейсе задач и одном канале уведомлений. Главные условия — не расширять объем после старта и получить полностью интегрированный MVP к концу 5-й недели, оставив время на проверку и выпуск.
