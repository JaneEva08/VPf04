# Отчёт по тестированию трёх кейс-промптов (VPf04)

Курс: «Профессия вайб-кодер», модуль 7 «Внедрение ИИ».
Запуск: `python .\prompt_chat.py`, модель GPT-4o mini, температура по умолчанию 0.7 (дополнительно 0.1 и 1.0).

## Что такое кейс-промпт

Кейс-промпт — заранее подготовленный шаблон инструкции для ИИ. В нём уже заданы роль, контекст, структура и формат вывода. Остаётся передать только саму задачу. Хороший промпт состоит из четырёх элементов: **роль, контекст, задача, формат вывода**. Главная причина плохих результатов — недостаток конкретики («Перескажи текст», «Сделай скелет сайта», «Реализуй приложение»).

---

## 1. Summary Prompt (резюме текста) — `01_summary_prompt.json`

**Назначение.** Сжать длинный текст до ключевых идей, сохранив смысл.

**Устройство промпта.**
- Роль: опытный редактор и аналитик текстов.
- Структура резюме: Заголовок → Основная идея (1–2 предложения) → Ключевые пункты (3–7) → Важные детали (факты, цифры) → Выводы и заключение.
- Формат: объём 15–25% от исходного текста, деловой стиль, сохранение хронологии и точности фактов, без вольных интерпретаций.
- Есть три примера, инструкция по использованию и тестовый вход (текст о проникновении ИИ во все сферы жизни).

**Тест.** Запуск с первым тестовым текстом (ввод `y`), температура 0.7, затем 0.1 и 1.0.

**Результаты.**
- При 0.7 получено подробное структурированное резюме по заданным разделам.
- При 0.1 смысл сохраняется, меняются только формулировки; разница минимальна.
- При 1.0 вариант более креативный по языку, но структура и смысл те же.

**Вывод.** При чётко описанных роли, контексте и структуре температура почти не влияет на результат. Даже при максимальной случайности смысл сохраняется.

## 2. Code Structure Prompt (структура кода) — `02_code_structure.json`

**Назначение.** Получить «скелет» проекта (архитектуру, дерево файлов и модулей), а не готовый код. Это промежуточный этап перед написанием кода.

**Устройство промпта.**
- Роль: senior software architect с 15+ годами опыта.
- Компоненты: общая архитектура, структура директорий, модули, паттерны, API, схема БД, конфигурация, тесты.
- Требования: DRY, разделение ответственности, Dependency Injection, SOLID, модульное тестирование, лёгкий рефакторинг. Структура выводится иерархически, с комментариями.
- Примеры: FastAPI, React + TypeScript + Redux, микросервисы на Node.js, Flutter.

**Тест.** Интернет-магазин на FastAPI + React: PostgreSQL, JWT-аутентификация, файловое хранилище для изображений, обработка заказов, админ-панель, e-mail-уведомления, платежи, отзывы и рейтинги. Настройки по умолчанию.

**Результаты.** Модель выдала ответ из 10 разделов:
1. Общая архитектура: backend на FastAPI, frontend на React + TypeScript, микросервисный подход.
2. Backend: `app/main.py`, `api/v1`, `models`, `services`, `utils`, `tests`, `requirements.txt`, `docker-compose.yml`.
3. Frontend: `public`, `src`, `index.tsx`, `components`, `pages`, `services`, `utils`, `package.json`, `README.md`.
4. Основные модули: API, модели, сервисы, утилиты.
5. Паттерны: MVC, Repository и Service Layer, Dependency Injection.
6. API: CRUD для `/products` и `/orders` (GET, POST, PUT, DELETE).
7. БД: продукты, пользователи, заказы, отзывы и оценки.
8. Конфигурация и тесты.

При температуре 1.0 тексты различаются только словами, структура и логика совпадают.

**Замечания.**
- В ответе встречаются неточности. Заявлен «микросервисный подход», а описан модульный монолит с `docker-compose`, то есть архитектурное решение сформулировано нечётко.
- Заявлены MVC и JWT, но маршруты аутентификации в списке API не перечислены. Отдельных эндпоинтов для отзывов, платежей и админки тоже нет.
- Результат лучше рассматривать как черновик, который нужно проверить.

**Вывод.** Промпт даёт понятную модульную структуру, которую можно сохранить в файл и передать агенту Cursor для реализации. Температура определяет разнообразие формулировок, но не структуру: при низких значениях результат предсказуемее, при высоких больше вариантов слов.

## 3. Task Planning Prompt (планирование задач) — `03_task_planning_prompt.json`

**Назначение.** Систематическое планирование и декомпозиция задач проекта.

**Устройство промпта.**
- Роль: project manager (PMP, Scrum Master, 10+ лет в IT).
- Компоненты: цель, этапы, декомпозиция, зависимости, приоритизация (Must/Should/Nice to Have), оценка времени, ресурсы, риски, чекпоинты и метрики.
- Формат: Цель → Этапы → Задачи → Подзадачи. Критерии SMART, буфер 20–30%, критический путь.

**Тест.** Пример 3: MVP SaaS-приложения для управления задачами. Команда: 2 frontend-разработчика (React), 1 backend-разработчик (FastAPI), 1 дизайнер. Срок 8 недель, бюджет ограничен.

**Результаты.**
- Цель: быстро проверить идею на рынке и получить обратную связь.
- Этапы: 1) анализ требований и планирование, 2) проектирование интерфейса и прототипирование, 3) разработка backend (БД, регистрация и аутентификация, CRUD API), 4) разработка frontend (интерфейсы регистрации, проектов и задач, интеграция с API).
- Зависимости: backend завершается до frontend, тестирование зависит от обеих частей, развёртывание зависит от тестирования.
- Приоритеты: Must Have — регистрация, проекты, задачи с дедлайнами; Should Have — исполнители и статусы; Nice to Have — уведомления о дедлайнах.
- Также получены разделы про время, ресурсы, риски и чекпоинты.

**Замечание.** Условие «backend до frontend» неудачно для команды из двух frontend-разработчиков: они простаивали бы. Реалистичнее вести работу параллельно по согласованному контракту API.

**Вывод.** Промпт даёт полный и структурированный план с учётом ограничений, который можно уточнять запросами вроде «углубись в этап» или «пересмотри приоритеты».

---

## Общие выводы

1. Структура JSON-промпта (роль, контекст, структура компонентов, формат, примеры, инструкция) делает ответы предсказуемыми и полными.
2. Температура влияет на формулировки, а не на смысл и структуру: 0.1 даёт более предсказуемый текст, 1.0 — более вариативный.
3. Промпты можно связывать в цепочку: планирование → структура кода → реализация в Cursor. Структуру проекта сохраняют в файл и передают агенту.
4. Кейс-промпты экономят время, помогают не писать промпт с нуля и позволяют вернуться к готовой заготовке в любой момент (например, при новом заказе на фрилансе).
5. Ответы модели нужно проверять: встречаются неточности и нестыковки (см. замечания выше).
