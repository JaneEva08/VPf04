# План разработки MVP SaaS-приложения управления задачами

## 1. Общая цель проекта

За 8 недель выпустить веб-приложение, в котором пользователь может зарегистрироваться, создавать проекты, добавлять задачи, назначать исполнителей и получать уведомления о приближающихся дедлайнах.

**Критерии готовности MVP:**
- пользователь регистрируется и входит в систему;
- видит только доступные ему проекты и задачи;
- может создавать проекты и приглашать/добавлять участников;
- может создавать и редактировать задачи с приоритетом, статусом, дедлайном и исполнителем;
- получает email-уведомление о приближении дедлайна;
- приложение развернуто в доступном тестовом/production-окружении.

**Допущения для планирования:**
- MVP — адаптивное веб-приложение, без мобильных приложений;
- один часовой пояс или хранение времени в UTC с отображением в часовом поясе пользователя;
- уведомления отправляются по email, без push-уведомлений;
- совместная работа ограничена участниками проекта; роли и сложные права доступа не входят в MVP;
- оценка дана в часах работы команды, без учета внешних согласований.

## 4. Зависимости и критический путь

Основная последовательность:

**Согласование сценариев и модели данных → настройка backend → аутентификация → проекты и участники → задачи → уведомления → интеграционное тестирование → релиз.**

Ключевые блокирующие зависимости:
- frontend-интеграция зависит от согласованных контрактов API и ранней публикации схемы OpenAPI;
- управление задачами зависит от готовых проектов, пользователей и правил доступа;
- назначение исполнителя зависит от списка участников проекта;
- email-уведомления зависят от наличия дедлайнов, адреса исполнителя и фонового запуска;
- production-релиз зависит от настройки окружения, секретов и проверки сценариев доступа.

**Критический путь:** аутентификация → проекты/участники → API задач → интеграция frontend и backend → уведомления → приемочное тестирование → релиз.  
Рекомендуется выпускать API поэтапно и согласовывать контракты до начала параллельной UI-интеграции.

## 5. Приоритизация

**Must Have — без этого MVP не выполняет основную задачу:**
- регистрация, вход и выход;
- создание и управление проектами;
- управление участниками, необходимое для назначения исполнителя;
- создание, редактирование и просмотр задач;
- приоритеты, статусы и дедлайны;
- назначение исполнителя;
- email-уведомление о приближении дедлайна;
- контроль доступа между пользователями и проектами;
- базовое тестирование и production-развертывание.

**Should Have — включать, если укладывается в срок:**
- фильтры по статусу и исполнителю;
- аккуратная адаптация для мобильных экранов;
- базовый мониторинг и пользовательская документация;
- добавление участников только по email уже зарегистрированного пользователя.

**Nice to Have — после MVP:**
- приглашения новых пользователей по ссылке;
- повторяющиеся задачи и настраиваемые напоминания;
- комментарии и вложения;
- уведомления в Slack/Telegram или push;
- доска Kanban с перетаскиванием;
- расширенные роли и аудит действий.

## 6. Оценка времени и загрузки

Ориентир для планирования — до **30 продуктивных часов на человека в неделю** с учетом встреч, ревью и коммуникации. Это дает около 240 часов на специалиста за 8 недель; реальная доступность команды должна быть подтверждена в начале проекта.

| Роль | Ориентировочная загрузка | Основная ответственность |
|---|---:|---|
| Frontend-разработчик 1 | 170–200 ч | Архитектура frontend, вход, страницы проектов, интеграция |
| Frontend-разработчик 2 | 160–190 ч | Компоненты задач, формы, фильтры, UI-проверки |
| Backend-разработчик | 190–220 ч | API, БД, аутентификация, доступы, фоновые уведомления, деплой |
| Дизайнер | 65–85 ч | Сценарии, макеты, UI-kit, шаблон письма, финальная проверка UX |

Backend — наиболее вероятное узкое место. Чтобы снизить риск, backend-разработчику нужно в первую неделю зафиксировать API-контракты и быстро подготовить тестовые данные/заглушки, чтобы frontend-команда могла работать параллельно.

## 7. Необходимые ресурсы и низкозатратный стек

- **Frontend:** React, TypeScript при наличии опыта, бесплатный или недорогой хостинг статического приложения.
- **Backend:** Python, FastAPI, OpenAPI/Swagger.
- **База данных:** PostgreSQL на бесплатном/стартовом тарифе либо недорогой управляемый сервис.
- **Развертывание:** бесплатный или недорогой облачный тариф; проверить ограничения по фоновой обработке и времени работы приложения.
- **Фоновые задачи:** простой планировщик для MVP, запускающий проверку дедлайнов раз в час или раз в день. Выбирать решение, совместимое с хостингом.
- **Email:** провайдер с бесплатным стартовым лимитом; до релиза проверить подтверждение домена, ограничения тарифа и доставляемость.
- **Дизайн и коммуникации:** бесплатные тарифы Figma и трекера задач.
- **Безопасность:** хранение секретов в переменных окружения, хеширование паролей, проверка доступа на сервере, HTTPS.

Бесплатные тарифы могут иметь лимиты, режим сна или ограничения на фоновые процессы. Перед выбором хостинга проверить их на тестовом окружении, чтобы уведомления не зависели от постоянно работающего сервиса, которого тариф не гарантирует.

## 8. Риски и минимизация

| Риск | Вероятность / влияние | Минимизация |
|---|---|---|
| Backend становится узким местом | Средняя / высокое | Ранние API-контракты, ограничить MVP, параллельно использовать mock API |
| Задержки подключения email или проблемы с доставкой | Средняя / среднее | Проверить провайдера на неделе 2–3, сделать отправку независимым модулем |
| Бесплатный хостинг не поддерживает надежные фоновые задачи | Средняя / высокое | Проверить ограничения заранее; при необходимости использовать внешний scheduler или недорогой тариф |
| Ошибки разграничения доступа между проектами | Низкая–средняя / высокое | Проверять права на сервере для каждого запроса, добавить негативные тесты |
| Изменения требований во время разработки | Высокая / среднее | Зафиксировать MVP, новые функции направлять в backlog после релиза |
| Недооценка интеграции frontend/backend | Средняя / высокое | Еженедельные интеграционные сборки, демонстрация работающего сценария с недели 3 |
| Уведомления отправляются повторно или с неверным временем | Средняя / среднее | Хранить состояние отправки, согласовать часовой пояс, протестировать повторный запуск |
| Болезни или недоступность одного специалиста | Низкая–средняя / высокое | Документировать решения, проводить code review, сохранять резерв времени |

## 9. Чекпоинты и метрики

- **Конец недели 1:** согласованы scope, пользовательские сценарии и основные экраны.
- **Конец недели 2:** frontend и backend запускаются, базовый CI работает, контракты API опубликованы.
- **Конец недели 3:** пользователь может зарегистрироваться/войти и создать проект.
- **Конец недели 4:** проект содержит участников, базовый сценарий доступа проверен.
- **Конец недели 6:** можно создать задачу, назначить исполнителя, установить дедлайн и получить тестовое уведомление.
- **Конец недели 7:** пройдены основные сквозные сценарии, нет открытых критических дефектов.
- **Конец недели 8:** MVP развернут, релизная проверка пройдена, есть инструкция и канал для сообщений об ошибках.

**Метрики релизной готовности:**
- все обязательные сценарии из чек-листа проходят;
- нет открытых дефектов уровня блокер/критический;
- доступ к проектам и задачам проверен тестами;
- успешное создание и выполнение как минимум одного сценария уведомления;
- приложение доступно по HTTPS, ошибки фиксируются в логах.

Приоритеты и объем задач следует пересматривать раз в неделю. Если график начинает отставать, исключать функции с приоритетом Should Have и Nice to Have, сохраняя защиту данных, ключевые сценарии, тестирование и буфер стабилизации.
